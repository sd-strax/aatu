# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository nature

This repo is the **reckon OSS engine** — design specifications today, code starting Week 1 of Phase A. Currently private on GitHub; goes public at Phase H. **Treat every edit as if it's already public.**

Paid modules and commercial strategy live in the separate private repo `reckon-enterprise` (`github.com/sd-strax/reckon-enterprise`). That repo depends on this one as a Go module and implements the `module/` interfaces; this repo has zero awareness of it. The repo boundary is the architectural enforcement of the open-core split.

See "Public OSS posture" below — it is load-bearing for every edit.

## The product (reckon)

"Cursor for SOC analysts" — an AI-native investigation environment for threat hunters and IR responders (not T1/T2 triage). Substrate: **VS Code extension (primary), CLI (secondary), Go backend, transport-neutral capability layer for tool federation** (adapter classes: MCP, NATIVE_API, CUSTOM, FIXTURE, SOAR_PLAYBOOK; see `design/03-capability-layer.md` §5.4). v0 prototype runs against OCSF fixtures via the fixture adapter, not real tenants.

Two workflows, same loop, different entry points: **investigation** (entity-rooted) and **hunt** (hypothesis-rooted).

## Architectural commitments (load-bearing across specs)

These are decisions that have been ruled out of re-litigation in `01-domain-model.md`. Don't propose changes to them without explicit user direction:

- **Two-layer graph.** Telemetry layer = raw OCSF events, immutable. Interpretation layer = STIX-shaped objects, mutable. Joined by typed edges, never by embedding.
- **STIX 2.1 vocabulary** for the interpretation layer; **OCSF** for telemetry payloads. Adopted, not invented.
- **Identity is deterministic UUIDv5** (STIX rules). Same entity → same id across producers and investigations. Aliasing is an explicit edge, never a destructive merge.
- **Investigation = STIX Grouping + four extensions** (Seed, Lifecycle, ReasoningThread, ConclusionSlot).
- **`x-interpretation` is the only invented primitive** in the domain model. Hypotheses, predictions, findings are outputs of Interpretations, not separate primitives. (`04-action-authorization.md` adds `x-action` as a sibling, with explicit justification.)
- **Investigation aggregate is event-sourced; everything else is CRUD + thin history.** Postgres single events table, no ES framework. Atomic event-append + projection-update in one transaction.
- **AI is a delegate, never a principal.** Every event records a human principal; `actor.delegate` captures the AI. Authorization is the *intersection* of principal permissions and delegate policy.
- **Capability layer is pure I/O + normalization.** It does not reason, never produces `x-interpretation`, always emits `derivation_mode = DIRECT`. Only exception: detection_finding normalizer (`03-capability-layer.md` §4.12).
- **Blast radius, not action verb, drives the trust tier.** T2→T3 escalator at >10 distinct targets is non-negotiable in code, only adjustable.
- **Open core: paid layers on OSS, no overlap.** OSS engine lives in `reckon` (public-bound); paid modules live in a separate private `reckon-enterprise` repo that depends on `reckon` as a Go module and implements its `module/` interfaces. OSS has zero awareness of paid; the repo boundary enforces this. See `implementation/module-layout.md`.

## Public OSS posture

This repo is destined to be public OSS. Every edit must respect that. The following kinds of content do **not** belong here — they belong in `reckon-enterprise`:

- **Buyer profiles** ("MSSP," "in-house SOC," "the buyer pays per...")
- **Conversion economics** (revenue framing, conversion events, pricing/licensing terms beyond "licensing is bolt-on")
- **Commercial commitments** ("the product won't," "no third conversion hook")
- **Team-shape framing** (founder, Claude Code, Claude Design, hunter, contractor, hiring, calendar weeks/months)
- **Customer-specific context** (design partners by name, customer pull anecdotes, internal stakeholder names)
- **Competitive positioning vs SOAR/EDR/SIEM vendors by name** (generic capability comparisons are fine)

What stays here: architectural facts — what the codebase does, how it's structured, the rationale for the tradeoffs a contributor would need to understand.

**When in doubt, write the sentence in `reckon-enterprise`** and surface only the architectural distillation here, if any survives.

A pre-commit hook lands in Week 1 alongside Claude Code workflow setup (per `reckon-enterprise/30-day-plan.md` item 1) to catch obvious commercial keywords on commit. It is a backstop; the discipline lives here.

## Conventions in the prose

- **"v0"** means the mock-fixtures prototype, not a shipping version. Many decisions are explicitly deferred to v1+ and called out as such — preserve those deferrals when editing.
- **Custom STIX objects** use the `x-` prefix per STIX convention: `x-hypothesis`, `x-prediction`, `x-action`, `x-host`, `x-registry-key`, `x-scheduled-task`, `x-group`, `x-interpretation`.
- **"Adopted vs invented"** sections (e.g., `01-domain-model.md`) are load-bearing — they justify why something isn't a new primitive. Don't invent without updating these.
- Specs end with **"Open questions" / "Deferred to v1+"** sections that are deliberate non-decisions; the model accommodates either resolution. Treat these as part of the design, not as TODOs.

## Commands

`make help` lists everything. The ones you'll reach for:

- `make build` — builds both binaries to `bin/`: `reckon` (CLI/supervisor) and `reckon-backend`.
- `make test` — fast suite: `go test -race -short ./...`. The `-short` flag skips the slow embedded-Postgres/Temporal/Keycloak lifecycle tests (those download and boot real subprocess binaries). Use this loop while developing.
- `make test-all` — full suite including the embedded-deps lifecycle tests (`go test -race -count=1 ./...`); ~60s warm, several minutes cold. Run before a PR that touches `supervisor/`.
- `make lint` — `golangci-lint run ./...` (requires `brew install golangci-lint`).
- `make ci` — lint + fast tests + build. The pre-commit / pre-PR gate.
- `make ci-full` — lint + full tests + build. Pre-release.
- `make hooks` — installs the OSS-leak pre-commit hook (`git config core.hooksPath .githooks/`). Run once after clone.
- `make eval` — the behavioral eval run (`design/10`): drives the real agent loop against a RUNNING local stack with the real model. Costs tokens (BYOK `ANTHROPIC_API_KEY`); env-gated (`RECKON_EVAL=1`), never part of `test`/`ci`.

Run a single test: `go test -race -run TestName ./aggregate/` (drop `-short` if it's a lifecycle test guarded by `testing.Short()`).

## Code architecture (Phase A)

The code is younger than the specs, but the skeletons are nearly gone — only the `RenormalizePass` workflow body and paid-module stubs remain unfilled. The wired-up spine today is the supervisor, the runtime/module seam, the event-sourced aggregate, the auth gates, the Temporal worker (`temporal/`, workflow bodies still Phase C+), and the observability layer (`telemetry/`). Phase B is in progress: `identity/` is built; `capability/` has the adapter contract and fixture adapter, with normalizers and the verb resolver still to land.

**Two binaries, one shared runtime.** `cmd/reckon` is the CLI/supervisor (`start`/`stop`/`status`/`check`/`version`); the whole stack is assembled in `runtime.serve` (`runtime.Run` = activate modules + serve; `runtime.Preflight` = activate only, backing the `check` command). `cmd/reckon-backend` is a ~20-line `main` that injects an OSS `module.Registry` (disabled stubs) into `runtime.Run`. **`runtime.Run` + a `ModuleBuilder` closure is the only place OSS and paid binaries diverge** — this is the architectural enforcement of the open-core split. The paid binary (in `reckon-enterprise`) mirrors `cmd/reckon-backend` with a builder that returns real `module.Tenancy`/`module.Governance` implementations. OSS always uses `module.DisabledTenancy`/`DisabledGovernance`; if a config sets `paid.*` keys against an OSS binary, `runtime.Run` warns and continues.

**Supervisor (`supervisor/`).** Manages the bundled-deps stack as ordered `Component`s: Postgres → Temporal → Keycloak → Temporal-worker → Backend. Each implements the `Component` interface (`Name`/`Start`/`Stop`/`Health`); components hold their lifecycle state under a mutex because `Health` runs concurrently with watcher-driven `Stop`/`Start`. Start in registration order, stop in reverse. `RestartPolicy` is `FatalOnExit` (Postgres — unclean exit risks corruption) or `RestartOnExit` (everything else); `Supervisor.Run` starts a per-component watcher goroutine that polls health and applies the policy (budgeted restarts in a sliding window, escalation to fatal on exhaustion). Postgres/Temporal/Keycloak are real embedded subprocess binaries downloaded on first run — this is why the lifecycle tests are slow and `-short`-gated.

**Event-sourced aggregate (`aggregate/`).** The investigation aggregate is the *only* event-sourced thing; everything else is CRUD + thin history (an architectural commitment, see above). No ES framework — a single Postgres `events` table. The core invariant: `Handler.Handle` runs command→events translation, event-append, and every projector's `Apply` **inside one transaction** (`handler.go`). The Handler loads the stream in-tx, `foldState` folds it into current state, and `applyCommand` is a pure function (envelope + command + folded state → events). Optimistic concurrency via the `(aggregate_id, sequence_no)` primary key — a lost race returns `ErrConcurrent` and callers reload+retry. `Projector`s apply in-tx so the read model can never disagree with the event log; `Reset`+replay rebuilds projections from scratch, always ordered by `(aggregate_id, sequence_no)` — never by `occurred_at`, which is caller-supplied wall-clock time with no monotonicity guarantee. **Phase C.1** added the `x-action` lifecycle here (`04 §3`, `action.go`): x-actions are aggregate-internal (not in the external STIX store), driven by eight `action.*` events whose status is a projection (`action_current`), each transition paired with an `action-*` Interpretation (the eighth, `action.reversal_attempted`, records an unverified reversal attempt WITHOUT a status change — `04 §7.1`). Two guards live at the command handler — the actor/approver invariant (`actor.principal` must equal the recorded approver) and AI write-protection (`Actor.Kind == AI_DELEGATED` may `RequestAction` but never approve/reject/expire) — enforced at the same layer as the OCC check so no alternate code path bypasses them. Dispatch/result/reversal events (`action.dispatched`/`resulted`/`reversed`) are defined and folded but emitted by the Temporal `ActionLifecycle` workflow in C.4.

**Auth: two gates (`authz/`).** Gate 1 (RBAC) is live — `authz.Verifier` validates Keycloak JWTs against the realm's JWKS (discovered via OIDC `.well-known`), `RequireAuth` middleware extracts `Claims` into request context (`FromContext`). Gate 2 (action authorization) is a stub that auto-approves; the real CEL-based engine lands in `action/` at Phase C. Roles live in the IdP and travel in JWTs — reckon never caches or mirrors them. The `authz/action.go` stub is deliberately call-site-stable so inserting the real engine later only changes the constructor and decision shape.

**Server (`server/`).** `Backend` is the in-process HTTP server and itself a `supervisor.Component`. Dependencies arrive as connection strings (Pg DSN, Temporal host:port, Keycloak issuer URL) plus an injected `*aggregate.Handler` — it depends on *reachable services*, not on the components that brought them up, so it can be repointed at managed deps without touching the supervisor seam. `Start` runs a dependency probe (e.g. fetches Keycloak's OIDC discovery and asserts the issuer) before accepting traffic.

**Temporal worker (`temporal/`).** The in-process worker (`worker.go`) is a `supervisor.Component` that polls the `reckon` task queue — no separate worker binary (`05 §3.3`); it runs in the backend's process. A.7 registered the workflow inventory under stable type names; `ActionLifecycle`/`ReversalSaga` (C.4), `ArchiveInvestigation`/`PostConclusionPipeline` (D.5), and `SummarizeForKnowledgeIndex` (K3) are now filled, leaving only `RenormalizePass` as a skeleton that still fails fast with `Unimplemented`. **K3** filled `SummarizeForKnowledgeIndex` (`summary.go` + `summary_activities.go`) — the post-conclusion producer that reads a CONCLUDED investigation (projection + hypotheses + actions + event-span), extracts the design/06 §3.2 structured summary as a **pure function** (`buildSummary`: seed kind/value, MITRE techniques from hypothesis labels, actions_taken, crude conclusion_outcome, duration), renders a deterministic recallable body (the LLM-narrative seam — `GeneratorModel` empty until a server-side LLM client lands), and writes it through the `knowledge.Store.WriteSummary` consumer facade into the substrate's DERIVED `case-summaries` corpus (re-derivation is a revision via a reserved `__case_source:` tag, so it's idempotent under retry). Extraction (investigation/STIX domain) lives in `temporal/`; the substrate mapping lives entirely behind the knowledge facade. The narrative is **two-tier** (`06 §3.2` as amended): the server tier is this deterministic baseline — **the backend holds no model key, ever** — and the *client* tier enriches it at conclude-time: the workbench fires `transport.summarizeConcluded` after a successful conclude → sidecar `summarizeConcluded` method → `agent.Session.SummarizeConcluded` runs ONE no-tools BYOK completion over the session's own conversation (rehydrating from the thread if fresh) and POSTs `/api/knowledge/summary_narrative` (analyst role) → `knowledge.EnrichSummary` revises the baseline (body → narrative, `generator_model` stamped, structured tags/meta carried; `ErrNoSummary`→404 with a single client retry for the pipeline race). Fire-and-forget: a narrative failure never fails a conclude. **Candidate-SOP generation** (the compounding loop) rides the same conclude hook and client plane: the workbench also fires `transport.proposeSOP` → sidecar `proposeSOP` → `agent.Session.ProposeSOP` runs ONE no-tools BYOK completion that GENERALIZES a reusable SOP across this case + the SOPs/similar past cases the session consulted (or returns `warranted:false` — no duplicate of an existing SOP), and returns the `SOPCandidate` (NOT persisted). The workbench opens it as an editable markdown draft and prompts **Add to SOP library** / **Discard**; Accept imports the (possibly-edited) current buffer through the existing `/api/sops/import_markdown` path with a `reckon://investigation/<id>` source URL (so re-accepting revises rather than duplicates). The human decides both what is acted on and what is learned. This closes the loop the demo seed (`demo/knowledge`) primes: a concluded case teaches the corpus, and the next investigation's knowledge rail surfaces it. It runs as **step 2 of `PostConclusionPipeline`** (`temporal.NewSummaryActivities(handler, knowledgeStore)` injected via `WithSummaryActivities`), **best-effort** per `07 §9.1` — a summary failure is recorded on `PostConclusionResult.SummaryErr` and never fails the conclusion (step 1, the signed bundle, is the load-bearing one). **Phase C.4** filled `ActionLifecycle` (`action_lifecycle.go` + `activities.go`) — the durable dispatch of an APPROVED action, the highest-correctness-stakes path (R15). It calls activities (which hold the aggregate handler + action resolver): the **dispatch-ledger guard** (`08 §6b` — `CheckDispatched` short-circuits if an `action.dispatched` already exists, so a replay/retrigger never double-executes), records `action.dispatched` **before** the outbound call (`adapter_request_id` = workflow id), dispatches under the retry budget (`04 §6.1`: 3 attempts, 2s/8s/30s; `FATAL_ERROR` non-retryable), and records `action.resulted` — with the honest residual on failure (`08 §6c`: FAILED + per-target UNKNOWN, never a success inference). The dispatch/result events are SYSTEM-only aggregate commands (`command.go` guard). `runtime.buildActionActivities` injects the activities when write bindings are configured. The **`request_action` HTTP endpoint** (`server/actions.go`, `POST /api/actions`, analyst role) ties it together: build x-action → Gate 2 → record request + `policy_evaluated` in one tx → on `AUTO_POLICY`, approve (attributed to the policy's accountable human) and `StartActionLifecycle` via the dispatch `Client`; else leave `PENDING_MANUAL`/`PENDING_TWO_PARTY`. `Actor.Kind` is derived from the JWT `delegate_kind` claim, never the body — closing the seam obligation so the baseline DENY (AI-no-T3) can't be spoofed. **`ReversalSaga`** (`reversal_saga.go`, `04 §7`) completes the write-side workflows: a reversal is a full x-action of the descriptor's `reversible_by` inverse type (same tier as the original), and the saga runs its `ActionLifecycle` as a child workflow, then — only if it fully took effect (SUCCEEDED; PARTIAL never over-claims) — emits on the original either `action.reversed` (REVERSIBLE original: status → REVERSED, `reversed_by_ref` set) or `action.reversal_attempted` (BEST_EFFORT original like `ioc.block`: `reversal_attempted_by_ref` set, status stays SUCCEEDED — `04 §7.1` Position C), both via SYSTEM-only commands (original must be SUCCEEDED). The classification is frozen onto the x-action at request time (`ActionRequested.reversibility`), so a catalog edit can't re-classify an in-flight action. A failed reversal leaves the original untouched (honest-state: never claim an undo we can't verify). The endpoint routes a request with `reversal_of_ref` to `StartReversalSaga` instead of `StartActionLifecycle`. Phase C's write path (request → Gate 2 → approve → dispatch → result → reverse) is complete for v0. Note the package name clashes with the SDK's `go.temporal.io/sdk/temporal`, aliased as `sdktemporal`.

**Observability (`telemetry/`).** Phase A.8: `telemetry.Setup` installs the global `slog` logger (level/format-configurable, with rolling file logs under `<data>/logs`) and the global OpenTelemetry tracer provider — configured with **no exporter** at v0 (spans are created and nested in-process but not shipped; an OTLP exporter slots in at v1 without touching call sites). It also builds a private Prometheus registry served at `/metrics`. The returned `Provider` injects an `HTTPMiddleware` (root server span + request metrics) and the metrics handler into the `server.Backend` by function/handler — server stays decoupled from `telemetry`. Spans nest HTTP → `aggregate.Handle` → `aggregate.project` in one trace; the aggregate emits its spans via the cached global tracer (`otel.Tracer`), which safely delegates to whatever provider `Setup` installs (inert but harmless in unit tests that never call `Setup`).

**Identity (`identity/`).** Phase B.1: the deterministic tenant-scoped UUIDv5 resolver (`03 §7`). Pure, stateless — holds only the tenant namespace UUID, computes `<type>--<uuidv5>` over canonical JSON of each type's identity-contributing fields. Implements the three deliberate STIX deviations (process on `(host, pid, created_time@1s)` with anonymous-random fallback; email-addr and user-account lowercased; `account_type` never folded). Two hard rules: adapters never compute STIX ids (the normalizer, via this resolver, is the single arbiter), and the resolver only *folds* (case/whitespace/format) — per-type *shaping* of inputs (`domain\user` composition, host-identifier tier, hash selection) is the calling normalizer's contract (`03 §7.4`).

**Capability (`capability/`).** Phase B.2/B.4/B.5 so far: the transport-neutral `Adapter` interface (`03 §5.3`) with five classes and the `§6.2` error taxonomy (`RETRY`/`FALLTHROUGH`/`UNHEALTHY`/`FATAL` as `*AdapterError`, branched on by the future resolver); the telemetry-layer types (`OcsfPayload` → immutable `OcsfEvent` at ingest); the `FixtureAdapter` replaying `fixtures/<scenario>/*.json` (`03 §9`); and the normalizer layer (`03 §4`) — the interpretation-layer types (`SCO`/`ObservedData`/`Relationship`/`Edge`/`Provenance`), a class-keyed `Registry` with an opaque default (`§4.13`), and the `process_activity`/`authentication` normalizers, all minting identity through the resolver via a shared `resultBuilder`. and the verb resolver (`03 §3`) — declarative verb→binding→adapter selection by priority, the sealed parameter-templating engine (`§3.3`: `${path}`/`?`/`?? default`/`| transforms`, validated at config-load), and the five-value `Coverage` classification (`§6.1`). `Resolver.Resolve` walks bindings, templates+invokes the applicable/healthy one(s), normalizes the OCSF output, and returns the `CapabilityResult` envelope. Invariants: pure I/O, no reasoning, never authors `x-interpretation`, `derivation_mode = DIRECT` (sole exception: the detection_finding normalizer, `03 §4.12`, still to land). The `CapabilityDescriptor` catalog + `list_capabilities` (`§2.8`, `§6.3`) classify each verb as available/degraded/unavailable from its bindings' health. Runtime wiring is live: `capability.LoadTenantConfig` + `BuildResolver` construct the resolver/catalog from a tenant capability YAML (`config.Capability.ConfigPath`), and `runtime.buildCapability` threads them into the backend, which serves `GET /api/capabilities`. The layer is optional in v0 — no config path leaves the route a clean 503. Normalizers cover all v0 OCSF classes (`§4.1`–`§4.12`): process/auth/network/dns/file, the persistence classes (registry-key/scheduled-job/module), account-change, email/email-url, the `detection_finding` INFERRED exception (Indicator + Sighting + vendor Identity, evidence recursed through the registry), and the Phase F `case` normalizer (`§2.9`, class 2005 Incident Finding → an `ObservedData` carrying case metadata in extensions, DIRECT derivation, no SCO extraction). The first fixture scenario ships as data: `fixtures/lateral-movement-via-rdp/` (OCSF events, `§9`) + `examples/capability/lateral-movement.yaml` (the tenant config binding four verbs to it), covered by a scenario smoke test. Phase B is complete for v0; the JSON-RPC/stdio transport for out-of-process adapters (`§5.4`) and real vendor adapters land in Phase E.

**Demo lifecycle (`config.Demo`, `reckon demo seed`/`reset`).** The bundled demo world is segregated from a real install behind a single switch, `config.Demo.Enabled` (default false). It gates two things. First, the **FIXTURE adapter class**: a `ClassFixture` binding is a hard error unless demo mode is on — enforced inside `capability.BuildResolverWithAdapters` **and** `action.BuildActionResolverWithAdapters` (both now take a `demo bool`), the single chokepoint every construction path funnels through (including the backend's hot-reload via `BackendConfig.Demo`), so a copied-in or hand-edited config can never run mock data/actions against a real deployment. Second, the seed/reset lifecycle. A plain `reckon init` now yields a **fixture-free** install (empty `Capability.ConfigPath`, `/api/capabilities` → clean 503) — it no longer auto-seeds. `reckon demo seed` (stack **up**) loads the embedded knowledge pack (`demo/knowledge/` — SOPs + prior-case summaries, embedded in `DemoFS`) over HTTP into `reckon_knowledge`, then materializes the fixtures + merged capability/action config via `runtime.SeedDemo` and flips `demo.enabled`; a restart activates the capabilities. The **virginity guard** is server-enforced at `POST /api/admin/demo/seed` (`server/demo.go`): it refuses (409 + counts) unless there are zero investigations and zero SOPs, so it can never contaminate a working instance. `reckon demo reset` (stack **down**) is the throwaway button: it removes `<data>/pg/data` (both reckon DBs re-init empty on next boot — no per-table archaeology against the event log) + Temporal's SQLite + seeded fixtures/config, and rewrites the config fixture-free; it refuses on a non-demo install without `--force`, and refuses while the backend is reachable. Keycloak (auth) + the secret store survive a reset. The mental model: test-drive the full product on fixtures, then cleanly graduate to real day-to-day data.

**Action / write side (`action/`).** Phase C.2: the symmetric twin of capability's read surface (`08`). `ActionDescriptor` catalog + `list_action_types` (available/degraded/unavailable), the `ActionBinding` model, and the **no-fall-through** action resolver — unlike the read resolver, once a binding is chosen a failed dispatch never retries against another tool (a partial state change must not be re-attempted). The `WriteAdapter` contract is `Dispatch(op, params, idempotency_key) → WriteResult` (an outcome, not an observation — no normalizer on the write path), with the layered idempotency key `f(x-action.id, target)`. `BuildRequestCommand` validates a `request_action` against the catalog, **requires ≥1 `evidence_ref`** (grounding is a mechanism, not a prompt convention — `09 §3`; reversals are exempt, grounded by `reversal_of_ref`, the same carve-out `10 §3`'s G1 makes), and applies the **blast-radius escalator** (`04 §1`: a T2 action over the threshold distinct targets → T3, non-negotiable) before emitting C.1's `aggregate.RequestAction`. The `FixtureWriteAdapter` ("fake Tines") replays declared `WriteResult`s from `fixtures/<scenario>/*.action.json`. It reuses capability's templating via the exported `capability.RenderParams`/`ValidateParamTemplates`/`LookupPath`. **Phase C.3 — Gate 2** (`gate2.go`/`policy.go`): the CEL auto-approval engine (`04 §4`) that replaces `authz.PermissiveGate2`. `Gate2.Evaluate` runs versioned CEL policies over a flattened `EvalInput`→`ctx.*` projection and resolves an authorization `Decision` by priority (DENY > REQUIRE_TWO_PARTY > AUTO_APPROVE > manual); the non-deletable **baseline DENY** (`AI-no-T3`) is always prepended, so an AI-delegated T3 can never auto-approve regardless of tenant policy. Shadow policies (`04 §4.4`) are evaluated + recorded (`would_have_fired`) but never drive the decision. `ApplyDecision` threads the evaluation onto the `RequestAction` command so the `action.policy_evaluated` audit event (`02 §3`) is written in the same transaction as `action.requested`. Uses `cel-go`; `any_in`/`all_in` are v0 list-membership helpers. The `request_action` HTTP endpoint + the ActionLifecycle/ReversalSaga workflow bodies land with C.4 — the endpoint must derive `Actor.Kind` from the JWT `delegate_kind` claim.

**Knowledge service (`knowledge/`).** Phase C.5, `design/06`: the SOP corpus over the separate `reckon_knowledge` DB. As of K2 it is the **consumer-side facade over the memory substrate** (below), not a direct-SQL store: `knowledge.NewStore(substrate.Store)` maps the SOP domain onto the substrate's `procedures` CURATED corpus and translates results back, reaching the mechanism only through the `substrate.Store` interface. A SOP's external id is a **stable lineage id carried in a reserved `__sop_lineage:` tag** (stripped from every user-facing tag list), so an edit becomes a substrate *revision* (prior content stays hash-addressable) while the id the server and audit trail reference never moves. `RecallSOPs` delegates to `substrate.Recall` (semantic when embeddings are configured, keyword fallback otherwise — attributed via `SOPMatch.Backend`); an empty query browses by tag (the substrate requires a query, so the facade owns the recency-browse path). Public API (`Create`/`Get`/`List`/`Update`/`Retire`/`RecallSOPs`, `SOP`/`RecallRequest`/`SOPMatch`/`RecallResult`) is unchanged, so `server/knowledge.go` is untouched. **Bulk import** (`06 §2.4`): markdown + YAML frontmatter → `knowledge.Import` — an **upsert keyed on `source.url`** (re-import = revision, same lineage id). Attribution keeps three facts distinct in entry meta: original author (frontmatter), source pointer (`system`/`url`/`version`), importer (the authenticated principal, server-recorded) + time. The markdown+frontmatter parser is shared (`internal/sopdoc`, `gopkg.in/yaml.v3`); richer formats convert at the edge (pandoc). Two entry points: the CLI `reckon knowledge import <files/dirs>` (`cmd/reckon/knowledge_cmd.go`, dev-auth ROPC, parses client-side → `POST /api/sops/import`), and the workbench **"Import SOPs…"** command (`reckon.importSOP`, `extension.ts`) — a file **picker** (native select, never the quick-bar; SOPs are consultative so import is an occasional *command*, not a management view, per the `design/13 §4` SOP-library-is-v1 phasing) that reads files client-side and `POST`s raw markdown to `/api/sops/import_markdown`, which parses server-side via `sopdoc`. Both land in the same corpus, instantly consultable in the knowledge rail. Exposed at `POST /api/knowledge/recall_sops` (reader) + `/api/sops` CRUD (analyst to write). Independent of the C.1–C.4 write path. The legacy `sops`/`investigation_summaries` tables are orphaned (a later cleanup drops them once K3 moves summaries onto the substrate too).

**Implicit retrieval + the injection dial (`06 §5.1`).** Knowledge is not only a tool: `agent.Session.retrieveImplicit` (in `refreshContext`) auto-recalls relevant SOPs + similar past cases against the seed context and **surfaces** them with their relevance signals (score, similarity band, `match_rationale`) rather than blindly injecting them. What enters the model's context is gated by a **posture dial** — `config.Knowledge.Injection`, a trust-dial sibling (validated at `buildKnowledge`, surfaced via `InvestigationView.knowledge_injection`): `"opt_in"` (default — nothing reaches the model until the analyst includes it; the controlled tryout) or `"auto"` (strong matches — SOPs, NEAR_DUPLICATE/RELATED cases — default in, DISTINCT stays off, analyst can veto). Both share one mechanism: `RetrievedKnowledge()` exposes the annotated items (the workbench rail, `createSession.knowledge`); `SetIncludedKnowledge(refs)` (driven by the turn's `included_knowledge` param) is the analyst's gate and rebuilds the system prompt to carry exactly the included set under `# Your organization's relevant SOPs…` / `# Similar past investigations…`; included items fold into `consulted_*` provenance (`§6`). The **workbench knowledge rail** (`investigationDocument.ts`, loaded on open for workable investigations) renders each item with a checkbox + band/rationale; the analyst curates, the selection rides the next turn. The dial only sets each item's *initial* inclusion — the analyst, not the retriever, decides what the AI reasons over.

**Similar-investigation recall (K4).** `RecallSimilar` runs SIMILARITY-mode recall over `case-summaries` (`POST /api/knowledge/recall_similar_investigations`, reader) — "have we handled something like this before?"; each match's `investigation_ref` is recovered from the reserved source tag (recall hits carry no provenance/meta), reserved tags stripped, substrate bands (NEAR_DUPLICATE/RELATED/DISTINCT) ride through. The agent gets a `recall_similar_investigations` tool; the session tracks retrievals (`trackConsultedSimilar`) and audit-links them onto the committed interpretation as `consulted_similar_investigations` (the `ConsultedSimilarInvestigation` audit field on `InterpretationRecorded`/`RecordInterpretation`, `06 §6`), with `Used` decided conservatively from the turn's own final text — the exact mirror of the existing `consulted_sops` path. The workbench renders "similar case" / "drew on case" chips alongside SOP chips. This closes the compounding loop: a concluded investigation (K3) is now recalled by similarity in later investigations, with the consultation on the audit trail.

**Config + wiring.** `config.Knowledge.Embeddings` (`base_url`/`api_key`/`model`) selects the semantic backend; `runtime.buildKnowledge` resolves the `api_key` **secret reference** at the composition root (`internal/secretref`) and injects a constructed `substrate.NewOpenAICompatEmbedder` via `WithEmbedder` — the substrate never reads config or resolves secrets. The substrate's schema rides `reckon_knowledge` under its **own migration-tracking table** (`supervisor.DatabaseSpec.ExtraMigrations` + `pgmigrate.RunWithTable`), so its versions don't collide with the host knowledge set on `schema_migrations`.

**Memory substrate (`knowledge/substrate/`).** The consumer-neutral storage/retrieval mechanism (`knowledge/design/00-substrate.md`) the knowledge service is re-based onto (its first consumer, wired in K2) — staged in-tree, destined for extraction to its own repo (§12 triggers). **Host-free by construction**: imports stdlib + third-party only, enforced by `TestImportBoundary`; reckon consumes it through the `substrate.Store` interface at the composition root, and no host vocabulary (tenants, STIX, investigations) crosses in — it sees an opaque `namespace` and generic entries. Two corpus archetypes (CURATED with lightweight/gated governance, DERIVED with provenance), revisions-as-rows (never content mutation, which makes the entries table the §6 snapshot store), RFC 8785 content-hash attestation (one-way door, `hash_version` 1), purge-with-tombstone. **Retrieval is vector-first**: one OpenAI-compatible embedder (`base_url` config covers OpenAI/Voyage hosted and Ollama/vLLM self-hosted alike; key is separate from the LLM key — Anthropic has no embeddings endpoint), write-time embedding that fails loudly, exact cosine in-process (corpora are hundreds-to-thousands of entries; no vector DB, deliberately — an ANN index slots behind `Recall` if ever needed), similarity bands NEAR_DUPLICATE/RELATED/DISTINCT with deployment-tunable cutoffs, keyword FTS only as the attributed degraded fallback, `Reindex` as the model-switch path. Own migrations (`substrate_*` tables); tests share the package-level embedded Pg (port 15438).

**Workbench (`workbench/`).** The analyst-facing VS Code extension (`design/13`) — TypeScript, in-tree, shipped as its own `.vsix` (Marketplace + OpenVSX + release-attached; never bundles the engine). Residence/packaging rationale: `implementation/module-layout.md` ("The workbench"). Currently the scaffold: reckon view container, Investigations placeholder, `/status` client; the v0 slice lands per `design/13 §7`. Build with `make workbench-ci` (Node; deliberately not part of `make ci` — engine work stays Go-only). Binding rules: the workbench discipline (`design/13 §3` — reckon-owned real estate only, commands over menus, no workspace-folder assumption) and zero paid awareness.

**Eval harness (`eval/`).** `design/10`: engineering infrastructure, not a product surface. Drives the shipped `agent.Session` through deterministic scenario driver scripts (`eval/scenarios/*.yaml` — ordered analyst turns + turn-scoped assertion ids, no branching) against a running local stack, then grades the **committed turn record** (`TurnResult.Transcript`/`ToolCalls` are byte-identical to the side-store commit — `Turn` fails when the commit fails) with deterministic graders keyed by the `10 §3` assertion ids (`Catalogue` in `graders.go`; v0 slice: H2/H3/H4/A2/A3/E1/E2/O1/O2 — event graders G1–G3 land when the APIs expose `evidence_refs`/ordering). Aggregation per `10 §4`: MUST = all-N-trials, SHOULD = pass rate, `NOT_EXERCISED` reported distinctly; every run is attributed (prompt hash, model, catalog hash, driver hash, catalogue version) and compared against a committed per-model baseline (`eval/baselines/`, regression rule `10 §4.4`). Grader unit tests are token-free and run in `make test`; the live run (`TestEvalRun`) is env-gated behind `make eval`. Artifacts (transcripts + report JSON) go to `eval/artifacts/`, gitignored.

**Migrations** live next to their owning package as embedded `fs.FS` (`aggregate/migrations/`, `knowledge/migrations/`) and are handed to the supervisor's Postgres component per-database (`reckon_main`, `reckon_knowledge`). Config schema is `config/config.go` (YAML; both binaries read the same schema).

`implementation/reckon-patterns.md` is the canonical short list of these patterns (pure-function + tx-wrapper, `Component` contract, two-axis auth chain, DI-by-connection-string, embedded-fs migrations, per-package `TestMain` with shared Pg). Read it once before writing new code in these packages.
